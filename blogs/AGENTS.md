# Blog publishing requirements

Every HTML page under `blogs/`, including posts, archives, topic pages and author pages, must use the shared footer in `templates/blog-footer.html` and load the generated `/blogs/assets/footer.min.css` and `/blogs/assets/footer.min.js`. Keep the shared cookie preferences control wired to the blog banner via `blogs/assets/footer.js`. The footer must be present in the generated HTML, not only injected by JavaScript.

After adding or editing a blog page, run `npm ci` once, then `npm run build:blogs` from the repository root before publishing. This synchronizes the footer from the main portfolio `index.html`, including its styles and shared SVG artwork, applies it to new and old pages, then generates minified JavaScript and CSS with content-based cache versions. The static footer artwork must render without JavaScript; the original inline SVG is restored near the viewport for animation. Preserve the existing skyline geometry and animated behaviour. Do not approximate the portfolio footer or fork its artwork, colours, spacing or typography. Preserve the existing page content, canonical URLs, metadata and header navigation. Validate internal anchors, one footer per page, social links, and cookie settings.

Archive pages must offer useful introductory guidance and contextual links, rather than an empty list of posts. Keep metadata titles concise and unique. Preserve the requested title on the blogs homepage. Avoid repeating large inline SVG markup across pages.

Managed new articles live in `blogs/content/<slug>.md` with matching JSON metadata. `scripts/build-posts.py` renders them, updates the archive cards, RSS and sitemap, and preserves original publication dates. Do not run the old scratch builder or replace unmanaged historical posts. Keep each new article's main body between 1,000 and 1,200 words, excluding headings, source notes and bylines. Preserve the existing `/blogs/` URLs and never reintroduce `/blog/`.

Before release, prepare contextual inbound links on useful existing pages, render the new article, then run `npm run build:blogs` and `npm run check:blogs`. Review the entire change set and publish atomically with a current-branch lease. Verify actual live HTML, media and affected links after GitHub Pages finishes. Never report a deployment as live from a commit response alone.

Keep private reports, analytics, connector details, editorial plans and source evidence outside this public repository. Use approved public professional context or educational guidance. Do not invent achievements, results or exact historical work dates. A contact click indicates intent and is not a confirmed enquiry. The shared measurement asset only sends events after analytics consent.
